# 시계열 데이터 추론 실습 (team2 Jetson) Constitution

## Core Principles

### I. 문서·비밀 보호

- 모든 답변·문서·보고서는 한국어로 쓴다. 코드 식별자·명령어만 원문을 유지한다.
- `README.md`는 과제 안내서이며 읽기 전용이다. 수정·덮어쓰기·이동을 금지한다
  (원본 해시: `.backup/README.sha256`).
- `.env`의 값은 어떤 출력·로그·커밋에도 노출하지 않는다. 코드는 `python-dotenv`로
  로드만 하고, 키 확인은 `cut -d= -f1 .env`로 한다.
- 이 규칙은 `.claude/hooks/protect.py` PreToolUse 훅이 강제한다.

근거: 과제 원문이 훼손되면 요구사항 추적이 끊기고, 브로커·DB 자격 증명은 팀 공용 자원이다.

### II. 엣지 자원 제약

- 실행 대상은 Jetson(L4T R39, aarch64, RAM 7.3GB, Python 3.12)이다. 모든 구성 요소는
  이 보드에서 돌아야 하며, 설계 시 메모리 예산을 명시한다(이후 로컬 LLM·임베딩 모델과 공존).
- sudo·Docker를 쓰지 않는다. 패키지는 `uv`로 `.venv`에만 설치하고 실행은 `.venv/bin/python`.
- 상시 실행은 systemd **사용자** 서비스로 하고, 재부팅 자동 시작은
  `loginctl enable-linger` 또는 `crontab @reboot`로 보장한다.

근거: 권한 없는 단일 보드에서 여러 서비스가 함께 돌아야 한다.

### III. 설정 주도

- 메시지 형식 변경, 센서·공간·항목 추가는 **코드 수정 없이 설정 파일만 바꿔** 대응할 수
  있어야 한다(MUST). 토픽 패턴, 필드 경로, 단위, 공간 매핑은 설정에 둔다.
- 설정은 시작 시 검증하고, 잘못된 설정은 명확한 오류로 거부한다.
- 접속 정보는 `.env`, 동작 설정은 버전 관리되는 설정 파일로 분리한다.

근거: 센서 종류와 형식은 바뀌고 늘어난다(과제 1 요구사항 2).

### IV. 테스트로 검증하는 확인 기준

- 과제 하나 = spec 하나(`specs/NNN-이름/`). README의 "해결할 것"은 요구사항,
  "확인 기준"은 수용 기준이 된다.
- 모든 확인 기준은 `pytest` 자동 테스트로 검증한다(예: 브로커 재시작 후 1분 내 재수집).
  자동화가 불가능한 기준(실제 재부팅 등)은 재현 절차와 측정 기록을 남긴다.
- 외부 자원(MQTT·MySQL) 의존 테스트는 표시(marker)로 분리해 오프라인 단위 테스트와 구분한다.

근거: 확인 기준은 평가 항목이며, 사람이 매번 손으로 확인하면 회귀를 놓친다.

### V. 공정한 평가

- 시험 기간 데이터를 학습·정규화 통계·모델 선택에 쓰지 않는다(누수 금지).
- 기준선과 모델은 같은 시점·같은 조건에서 비교한다.
- 모든 결과표에 측정 조건을 함께 적는다: 데이터 기간, 실데이터/합성 여부, 시험 기간,
  보드 전력 모드(성능 측정 시 클럭 고정 여부·반복·워밍업 포함).

근거: 평가 기준의 "공정한 평가" 영역이며, 조건 없는 숫자는 재현·비교할 수 없다.

### VI. 사람 손 없는 복구

- 브로커 재시작, 네트워크 끊김, DB 일시 장애, 보드 재부팅 뒤에 사람 개입 없이 다시
  동작해야 한다(MUST). 재접속은 지수 백오프와 상한을 두고, 프로세스 종료는 서비스
  관리자가 재시작한다.
- 한 번의 처리 실패가 서비스 전체를 멈추게 해서는 안 된다. 실패는 기록하고 다음 주기에 회복한다.
- 끊김·지연·실패는 숨기지 않고 상태(건수, 마지막 수신 시각, 커버율, 경보)로 드러낸다.

근거: 수집이 하루 멈추면 그날 데이터는 학습·평가에 쓸 수 없다.

### VII. 해석 우선

- 결과는 숫자만 나열하지 않는다. 각 결과마다 "왜 이렇게 나왔는가"와 "그래서 무엇을
  해야 하는가"를 함께 쓴다.
- 모델·탐지기가 못 하는 것과 결측 구간의 원인을 명시적으로 짚는다.

근거: 평가 비중이 가장 큰 영역(30%)이 해석이다.

## 운영 제약

- **저장소**: 수집 데이터는 MySQL 8.0(`cf_u36_d3`)에 저장한다. 팀 DB 안에서 DDL/DML이
  허용된다. 수집(쓰기)과 학습·추론(읽기)이 같은 저장소를 쓰므로, 읽기 작업이 쓰기를
  막지 않도록 인덱스·쿼리 범위를 설계한다.
- **원천**: MQTT 브로커(ChirpStack LoRaWAN, xflow 냉난방)는 구독만 한다.
- **InfluxDB**: 원본 대조용 조회 전용이며 현재 네트워크에서 접근할 수 없다. 이 자원에 의존하는
  기능을 필수 경로에 두지 않는다.
- **시각**: 센서 측정 시각과 수신 시각을 구분해 저장하는 것을 기본으로 한다.

## 개발 흐름

- Spec Kit 순서: `/speckit-constitution` → `/speckit-specify` → `/speckit-plan` →
  `/speckit-tasks` → `/speckit-implement`. 필요 시 `/speckit-clarify`, `/speckit-analyze`.
- plan 단계의 Constitution Check에서 위 7개 원칙 준수 여부를 확인하고, 위반은 근거와 함께
  Complexity Tracking에 기록한다.
- 과제 완료 시 `CLAUDE.md`의 진행 상황을 갱신한다.

## Governance

- 이 헌법은 프로젝트의 다른 관행보다 우선한다. 단, `CLAUDE.md`의 절대 규칙과 충돌하면
  `CLAUDE.md`를 따르고 이 문서를 맞춰 고친다.
- 개정은 변경 이유와 영향 범위를 Sync Impact Report로 남기고 팀 합의 후 반영한다.
- 버전은 유의적 버전을 따른다: 원칙 삭제·재정의는 MAJOR, 원칙·섹션 추가 또는 실질 확장은
  MINOR, 문구 정리는 PATCH.
- 모든 plan·리뷰는 이 원칙 준수 여부를 확인한다.
