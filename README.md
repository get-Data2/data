# 시계열 데이터 추론 실습 — 과제 안내

> 학습 공간의 센서 데이터로 **"지금 무슨 일이 일어나고 있고, 곧 어떻게 될까"**에 답하는 추론 기능을 만들어 Jetson에서 상시 운영한다.
> 이 문서는 **무엇을 해결해야 하는지**만 설명한다. 실행 방법은 README, 제공 코드의 동작 원리는 CODE_GUIDE를 본다.
> 팀 단위 · 팀 Jetson 1대

---

## 1. 배경

교육장(강의실 2, 회의실 1, 라운지 1)에는 CO₂·온도·습도 센서만 있다. 카메라는 없어서 **공간을 누가, 몇 명이 쓰고 있는지는 직접 알 수 없다.** 센서 값은 MQTT 브로커로 1분마다 들어온다. 대신 수업 시간표와 회의실 예약 같은 **일정 정보**는 미리 알 수 있다.

지금 운영진이 겪는 문제는 이렇다.

| 현장의 문제 | 데이터로 바꾼 질문 |
|---|---|
| 수업 중 CO₂가 1,500ppm을 넘고 나서야 환기한다. 이미 졸리고 머리가 아픈 뒤다 | **앞으로 60분 동안 CO₂·온도가 어떻게 변할까?** |
| 센서가 멈추거나 값이 틀어져도 며칠 동안 아무도 모른다. 냉방이 꺼져도 민원이 와야 안다 | **지금 들어오는 값이 평소와 다른가? 어느 센서가 이상한가?** |
| 공간이 실제로 쓰이는지 모른다. 예약해 놓고 안 쓰는 회의실, 빈 방에 켜진 냉난방을 알 수 없다 | **센서값만으로 공간이 쓰이고 있는지 알 수 있을까?** |
| 학습 데이터가 몇 주 분량뿐이다 | **우리 데이터로 학습하지 않은 범용 모델로도 쓸 만할까?** |
| 이 판단을 서버 없이 교육장 안 장비에서 끊김 없이 해야 한다 | **작은 보드에서 빠르고 안정적으로 돌릴 수 있을까?** |

이번 실습의 목표는 이 다섯 질문에 **숫자로 답하고**, 그 답을 다른 서비스(대시보드, 로컬 LLM 에이전트, 냉난방 제어)가 가져다 쓸 수 있는 **상시 서비스**로 만드는 것이다.

## 2. 데이터

| 항목 | 단위 | 원천 | 비고 |
|---|---|---|---|
| CO₂ | ppm | 환경 센서 | 외기 약 420ppm, 1,000ppm 이상이면 환기 권고 |
| 온도 | ℃ | 환경 센서 | 냉난방 가동 시간에만 설정 온도로 유지 |
| 습도 | % | 환경 센서 | |
| 일정 | — | 수업 시간표, 회의실 예약 | 센서가 아니라 운영 자료. **미래 값도 미리 알 수 있다.** 실제 사용과 다를 수 있다(결석, 노쇼, 연장) |

데이터에는 현장의 불완전함이 그대로 들어 있다. 게이트웨이 끊김으로 생긴 결측, 0ppm 같은 깨진 값, 측정 잡음이 섞여 있다. **이것을 처리하는 것도 과제의 일부다.**

실데이터가 3주 이상 쌓이기 전에는 합성 데이터 생성기를 쓴다. 합성 데이터는 수업 시간표·회의 예약·라운지 이용에 따라 CO₂·온도가 물리적으로 변하도록 만든 것이고, 같은 형식의 일정 자료가 함께 제공된다. 마지막 1주에는 정답을 아는 고장 5종이 심어져 있다.

## 3. 과제 구성

| 과제 | 해결할 문제 | 핵심 산출물 |
|---|---|---|
| 1. 데이터 수집 체계 | 끊기지 않고 쌓이는 시계열 저장소 | 상시 수집 서비스, 수집 현황 보고 |
| 2. 데이터 이해와 기준선 | 데이터가 믿을 만한가, 넘어야 할 선은 어디인가 | 데이터 진단서, 기준선 성능표 |
| 3. 60분 예측 | 앞으로 60분의 CO₂·온도 | 예측 모델, 기준선 대비 비교표 |
| 4. 이상 탐지 | 센서·설비 고장을 빨리, 헛경보 없이 | 탐지기, 고장 종류별 탐지 성적표 |
| 5. 상태 추정 | 센서값만으로 사용 여부 추정, 환기 선제 경보 | 분류 모델 2종, 혼동 행렬 분석 |
| 6. 사전학습 모델 비교 | 학습 없이 쓰는 범용 모델의 실력 | 비교표, 채택 여부 의견 |
| 7. 엣지 최적화 | 보드에서 빠르고 정확하게 | 최적화 보고서 |
| 8. 상시 추론 서비스 | 다른 시스템이 쓸 수 있는 형태로 운영 | 예측 서비스 v1, 12시간 가동 기록 |

트랙은 둘이다.

- **기본(A)**: 제공 키트를 실행하고, 결과를 해석하고, 정해진 질문에 답한다.
- **심화(B)**: 각 과제의 '심화' 항목을 직접 설계·구현하고, 제공 키트보다 나은 결과를 낸다.

어느 트랙이든 **결과 해석**이 가장 중요하다. "돌려 봤더니 이렇게 나왔다"가 아니라 "왜 이렇게 나왔고, 그래서 무엇을 해야 하는가"를 쓴다.

## 과제 1. 데이터 수집 체계

### 상황
모델은 데이터가 있어야 학습할 수 있다. 수집기가 하루만 멈춰도 그날은 학습에도 평가에도 쓸 수 없다. 센서마다 보내는 주기와 형식이 다르고, 앞으로 센서 종류가 늘어날 수 있다.

### 해결할 것
1. MQTT로 들어오는 센서 메시지를 받아 **공간·항목·시각별로 저장**하는 수집기를 상시 가동한다.
2. 메시지 형식이 바뀌거나 새 센서가 추가돼도 **프로그램을 고치지 않고 설정만 바꿔** 대응할 수 있어야 한다.
3. 브로커 재시작, 네트워크 끊김, 보드 재부팅 뒤에도 **사람 손 없이 다시 수집**되어야 한다.
4. "지금 데이터가 잘 쌓이고 있는가"를 한눈에 볼 수 있어야 한다. 공간·항목별 건수, 마지막 수신 시각, 커버율(1분 단위로 데이터가 있는 비율)이 필요하다.

### 확인 기준
- 브로커를 껐다 켜도 1분 안에 수집이 다시 시작된다
- 보드를 재부팅해도 수집이 자동으로 다시 시작된다
- 24시간 커버율 95% 이상, 빠진 구간이 있으면 원인을 설명할 수 있다

### 산출물
- 수집 현황 보고(공간·항목별 커버율 표, 결측 구간과 추정 원인)
- 메시지 형식을 바꿔야 하는 상황 하나를 가정하고, 무엇을 바꿔서 대응했는지 기록

### 생각해 볼 점
- 시각은 센서가 찍은 것과 수신한 것 중 무엇을 저장해야 하나? 네트워크가 30초 밀렸다가 한꺼번에 도착하면 어떻게 되나?
- 수집과 학습·추론이 같은 저장소를 동시에 쓰면 어떤 문제가 생기나?

### 심화(B)
- 저장소 크기가 1년 뒤 얼마가 될지 추정하고, 오래된 데이터를 줄이는(다운샘플링·보관) 정책을 설계한다.
- 같은 메시지가 두 번 오는 경우(재전송)를 찾아내고 처리한다.

## 과제 2. 데이터 이해와 기준선

### 상황
모델부터 만들고 싶겠지만, 데이터를 모르는 채 만든 모델은 왜 틀리는지 설명할 수 없다. 그리고 **아주 단순한 방법이 생각보다 강하다.** "지금 값이 60분 뒤에도 그대로일 것"이라는 예측조차 이기지 못하는 모델은 쓸 이유가 없다.

### 해결할 것
1. **정제 규칙을 정한다.** 아래 각각을 어떻게 처리할지 정하고 이유를 쓴다.
   - 물리적으로 불가능한 값(0ppm, 60℃ 등)
   - 짧은 결측(몇 분)과 긴 결측(몇 시간)
   - 센서마다 다른 기록 주기
2. **분석 간격을 정한다.** 1분 그대로 쓸지, 몇 분 단위로 모을지 정하고 근거를 쓴다.
3. **학습·검증·시험 기간을 나눈다.** 왜 무작위로 섞으면 안 되는지 설명할 수 있어야 한다.
4. **데이터를 진단한다.**
   - 공간별·항목별 결측률과 제거된 이상값 수
   - 평일 시간대별 평균 패턴(수업·점심·퇴실이 보이는가)
   - 수업 시작·점심·퇴실 같은 일정 변화 뒤 CO₂가 몇 분 만에 반응하는가, 일정과 실제 CO₂ 변화가 어긋나는 날은 언제인가
5. **기준선 3가지의 성능을 잰다.** 현재값 유지, 최근 1시간 평균, 어제 같은 시각이다. 5·15·30·60분 뒤 CO₂·온도 오차(MAE)를 비교한다.

### 확인 기준
- 정규화(평균·표준편차) 값을 **학습 기간 데이터로만** 계산했다
- 기준선 평가와 이후 모델 평가가 **같은 시점, 같은 조건**에서 이루어진다
- 세 기준선 중 무엇이 가장 강한지, 그 이유를 설명한다

### 산출물
- 데이터 진단서(1~2쪽): 정제 규칙, 분할 기준, 패턴 그래프, 일정–CO₂ 반응 분석
- 기준선 성능표

### 생각해 볼 점
- '어제 같은 시각'이 가장 약한 이유는 무엇인가? 어떤 공간이라면 이 방법이 강할까?
- 고장이 섞인 구간은 학습에 넣어야 할까, 빼야 할까? 평가에서는?

## 과제 3. 60분 예측

### 상황
환기는 CO₂가 기준을 넘기 **전에** 해야 효과가 있다. 냉난방도 미리 켜야 쾌적한 온도에 맞출 수 있다. 그래서 60분 앞까지 5분 간격으로 CO₂와 온도를 예측해야 한다.

### 해결할 것
1. **입력과 출력을 설계한다.**
   - 과거를 얼마나 볼 것인가(30분? 2시간? 하루?)
   - 어떤 정보를 넣을 것인가: CO₂·온도·습도, 시간대·요일, 어느 공간인지, 일정(수업·예약)
   - 60분을 한 번에 출력할지, 한 칸씩 반복해서 예측할지
2. **딥러닝 모델을 학습한다.** LSTM, GRU, TCN 중 최소 1종(B는 3종 비교)을 학습한다.
3. **기준선과 비교한다.** 과제 2와 같은 시점에서 5·15·30·60분 뒤 오차를 비교한다.
4. **공간별로 나눠 본다.** 어느 공간에서 잘 맞고 어느 공간에서 안 맞는지, 그 이유가 무엇인지 분석한다.
5. **일정 정보의 가치를 잰다.** 일정(수업·예약)을 입력에서 뺀 모델과 비교해, 일정 정보가 예측에 얼마나 기여하는지 숫자로 답한다.

### 확인 기준
- 60분 뒤 CO₂ 오차가 '현재값 유지'보다 **30% 이상 작다**
- 온도 60분 예측이 '현재값 유지'보다 좋다
- 시험 기간 데이터를 학습이나 모델 선택에 쓰지 않았다

### 산출물
- 모델 비교표(기준선 + 학습 모델, 예측 시점별 오차)
- 공간별 오차 분석과 그 원인
- 일정 정보 포함/제외 비교와 결론("일정 정보를 넣으면 60분 예측 오차가 ○ppm 줄어든다")

### 생각해 볼 점
- 회의실 예측이 다른 공간보다 어려운 이유는 무엇인가? 과거 센서값에 없는 정보는 무엇이고, 어디서 얻을 수 있나?
- 모델이 '지금 값'을 직접 예측하게 할 때와 '지금 값에서의 변화량'을 예측하게 할 때 무엇이 달라지나?
- 오차가 가장 큰 순간은 언제인가(수업 시작, 점심, 창문 개방)? 그 순간을 맞히는 것이 가능한가?

### 심화(B)
- 과거 길이(1시간·2시간·4시간)와 모델 종류를 바꿔 가며 비교하고, 최적 조합을 근거와 함께 제시한다.
- 회의실 예약·수업 시간표처럼 **미래에 알 수 있는 정보**를 입력에 넣는 방법을 설계하고, 회의실 예측이 개선되는지 보인다.
- 한 공간을 학습에서 완전히 빼고, 처음 보는 공간에서도 예측이 되는지(일반화) 시험한다.

## 과제 4. 이상 탐지

### 상황
고장은 종류마다 모습이 다르다. 한순간 튀는 값이 있고, 몇 시간 동안 같은 값만 보내는 센서가 있고, 하루에 걸쳐 조금씩 틀어지는 센서가 있다. 냉방이나 환기가 꺼지는 설비 고장도 있다. 경보를 너무 자주 울리면 운영자는 알림을 꺼 버리고, 너무 늦게 울리면 의미가 없다.

| 고장 | 현장 원인 | 데이터에서 보이는 모습 |
|---|---|---|
| 튄 값 | 통신 오류, 전기 잡음 | 한 칸만 크게 튐 |
| 값 고정 | 센서 멈춤, 게이트웨이가 마지막 값을 반복 | 1~4시간 동안 같은 값 |
| 영점 틀어짐 | CO₂ 센서 노화 | 수 시간에 걸쳐 수백 ppm 올라감 |
| 냉방 정지 | 실내기 고장 | 수업 중 온도가 서서히 3~5℃ 오름 |
| 환기 정지 | 환기 장치 고장 | 사용 중 CO₂ 상승 폭이 평소의 1.8배 |

### 해결할 것
1. **정상만 보고 이상을 찾는 모델**(오토인코더 등)을 학습한다. 실제 현장에는 '고장 정답'이 거의 없기 때문이다.
2. **경보 기준(임계값)을 정한다.** 기준을 어떻게 정했는지, 그 기준이 헛경보율과 어떻게 연결되는지 설명한다.
3. **규칙 기반 탐지**(급변, 값 고정)를 만들고 모델과 비교한다.
4. **고장 종류별로 평가한다.** 아래 네 지표를 낸다.
   - 이벤트 탐지율: 고장 몇 건 중 몇 건을 잡았나
   - 탐지 지연: 고장 시작부터 첫 경보까지 몇 분
   - 하루당 헛경보 수
   - 종류별 탐지 결과(각 종류마다 몇 건 중 몇 건)
5. **원인을 가리킨다.** 경보가 울렸을 때 어느 센서 때문인지 알려준다.

### 확인 기준
- 모델과 규칙을 합쳐 이벤트 탐지율 **80% 이상**
- 헛경보 **하루 1회 이하**(전체 공간 합)
- 모델이 못 잡는 고장 종류와 규칙이 못 잡는 고장 종류를 각각 찾아 이유를 설명한다

### 산출물
- 탐지 성적표(모델 / 규칙 / 결합 × 고장 종류)
- 임계값을 바꿨을 때 탐지율과 헛경보가 어떻게 변하는지 보여주는 표 또는 그래프
- 운영 제안: "이 공간에는 경보 기준을 ○으로, 알림은 ○○에게"

### 생각해 볼 점
- 센서가 정상 범위의 값에서 멈추면 왜 모델이 알아채지 못하나?
- 빈 방에서 환기가 멈추면 탐지할 수 있나? 탐지할 필요가 있나?
- 실데이터에서는 정답이 없다. 탐지기가 잘 동작하는지 어떻게 확인할 것인가?

### 심화(B)
- 과제 3의 **예측 오차**를 이상 점수로 쓰는 탐지기를 만들어 오토인코더와 비교한다.
- 가장 어려운 '영점 틀어짐'을 잡는 전용 방법을 설계한다(예: 사람이 없는 새벽의 CO₂는 외기와 비슷해야 한다는 사실 활용).

## 과제 5. 상태 추정

### 상황
두 가지 판단이 필요하다.

- **사용 여부 추정**: CO₂·온도·습도 변화만 보고 공간이 지금 쓰이고 있는지 판단하고 싶다. 사람이 숨 쉬면 CO₂가 오르고 체온으로 온도가 오르므로, 센서값에는 사용의 흔적이 남는다. 예약해 놓고 안 쓰는 회의실, 빈 방에 켜진 냉난방을 찾는 데 쓴다.
- **환기 선제 경보**: "지금은 괜찮지만 30분 안에 1,000ppm을 넘을 것"을 미리 알려 주고 싶다.

### 해결할 것
1. **정답을 정의한다.**
   - 사용 여부: 사용중 / 비어있음. 정답은 수업 시간표·회의실 예약에서 만든다. 일정은 실제 사용과 다를 수 있으므로(결석, 노쇼, 연장, 예약 없는 사용) 일부 시간대를 직접 관찰해 기록하고, 일정 기반 정답이 얼마나 틀리는지 먼저 확인한다.
   - 환기 경보: 무엇을 '양성'으로 볼 것인가. **이미 기준을 넘은 시점을 정답에 넣으면 왜 안 되는지** 설명한다.
2. **입력을 정한다.** 사용 여부 추정에는 일정 정보를 입력으로 쓰지 않는다. 정답을 일정에서 만들었는데 입력에도 넣으면 무슨 일이 생기는지 설명한다.
3. **분류 모델을 학습한다.**
4. **불균형을 다룬다.** 환기 경보 양성은 전체의 1~2%다. 정확도가 왜 의미 없는지 보이고, 의미 있는 지표로 평가한다.
5. **단순 규칙과 비교한다.** 예: 사용 여부는 "최근 15분 CO₂가 30ppm 이상 올랐으면 사용중", 환기 경보는 "현재 CO₂가 850ppm 이상이면 경보"

### 확인 기준
- 사용 여부 추정: 직접 관찰한 시간대 기준 정확도와 F1을 보고한다. '비어있음'인데 '사용중'으로 판단하는 오류율을 따로 보고한다(냉난방 자동 제어에서 가장 중요). 단순 규칙보다 좋아야 한다
- 환기 경보: '곧 환기 필요' 재현율 **85% 이상**, 단순 규칙보다 macro-F1이 높다
- 혼동 행렬을 보고 가장 많이 헷갈리는 경우를 설명한다

### 산출물
- 두 분류기의 성적표와 혼동 행렬
- 일정 기반 정답과 직접 관찰의 차이 분석
- "가장 많이 틀리는 상황"의 사례 분석(어떤 시간대, 어떤 공간, 왜)

### 생각해 볼 점
- 사람이 막 나간 직후의 빈 방은 왜 '사용중'으로 오판되기 쉬운가? 반대로 막 들어온 직후는?
- 적은 인원이 쓰는 큰 강의실은 센서로 구별할 수 있나? 공간 크기에 따라 무엇이 달라지나?
- 환기 경보의 정밀도가 낮으면(헛경보가 많으면) 현장에서 어떤 일이 생기나? 재현율과 정밀도 중 무엇을 우선해야 하나?
- 과제 3의 예측 모델로도 "30분 안에 1,000ppm 초과"를 판단할 수 있다. 분류기를 따로 두는 것이 나은가?

### 심화(B)
- 한 공간을 학습에서 빼고 그 공간에서 사용 여부 추정을 시험한다. 학습하지 않은 새 공간에도 바로 쓸 수 있는 수준인가?
- 예약 정보와 추정 사용 여부를 비교해 **회의실 노쇼**(예약 후 15분간 비어있음)와 **예약 없는 사용**을 찾아내는 규칙을 만들고, 직접 관찰 기록과 대조한다.

## 과제 6. 사전학습 모델 비교

### 상황
최근에는 수많은 시계열로 미리 학습해 두어, 우리 데이터로 학습하지 않고 과거 값만 주면 바로 예측하는 **시계열 파운데이션 모델**이 나와 있다(예: Chronos 계열). 학습 데이터가 적은 초기에, 혹은 새 공간에 바로 쓸 수 있다면 큰 장점이다. 대신 크고 느릴 수 있다.

### 해결할 것
1. 사전학습 모델 **1종 이상**으로 시험 기간 CO₂ 60분 예측을 수행한다(추가 학습 없음).
2. 같은 시점에서 **기준선 · 직접 학습한 모델 · 사전학습 모델**을 비교한다.
3. 사전학습 모델이 함께 주는 **예측 구간**(예: 10~90% 범위)이 실제로 얼마나 맞는지 확인한다. 이상적이면 80%가 구간 안에 들어와야 한다.
4. **비용을 잰다.** 보드에서의 1회 추론 시간과 메모리 사용량을 측정한다.
5. 우리 서비스에 **채택할지** 의견을 낸다.

### 확인 기준
- 세 방법을 같은 시점에서 비교했다
- 정확도, 예측 구간 적중률, 추론 시간, 메모리 네 가지로 판단 근거를 제시한다

### 산출물
- 비교표와 채택 의견(반 쪽)

### 생각해 볼 점
- 사전학습 모델은 CO₂ 과거값만 본다(다른 변수를 함께 받는 모델은 예외). 직접 학습한 모델과의 차이 중 얼마가 시간대·요일·온습도 정보 때문인가?
- 과거를 얼마나 길게 줄 때 가장 잘 맞나?
- 같은 보드에서 로컬 LLM(W4)과 함께 올려야 한다. 메모리 예산 안에 들어가나?

### 심화(B)
- 다른 변수(공변량)를 받을 수 있는 모델에 온습도·일정 정보를 함께 넣어 비교한다.
- 직접 학습한 모델과 사전학습 모델을 섞은 예측(평균 등)이 둘 다보다 나은지 본다.

## 과제 7. 엣지 최적화

### 상황
지금 모델은 작아서 CPU로도 빠르다. 그런데 이 보드에서는 앞으로 임베딩 모델, 로컬 LLM이 같이 돈다. 시계열 모델은 **최소한의 자원으로, 결과는 똑같이** 돌아야 한다.

### 해결할 것
1. 학습한 모델(예측·이상 탐지·분류)을 보드 전용 추론 엔진(TensorRT)으로 변환한다. 반정밀도(FP16)를 쓴다.
2. 아래 실행 방식의 **지연(평균·느린 쪽 5%)**을 잰다. 한 공간씩(배치 1)과 네 공간 한꺼번에(배치 4) 두 경우를 잰다.
   - PyTorch CPU, PyTorch GPU, ONNX Runtime, TensorRT
3. 변환 전후 **결과 차이를 원래 단위로** 잰다("CO₂ 예측이 최대 몇 ppm 달라졌나").
4. 측정 중 **전력·GPU·메모리 사용량**을 기록한다.

### 확인 기준
- 변환 후 CO₂ 예측 차이 **1ppm 이하**, 분류 결과가 바뀐 비율 0.1% 이하
- 측정 조건(전력 모드, 클럭 고정 여부, 반복 횟수, 워밍업)을 함께 기록했다

### 산출물
- 최적화 보고서: 실행 방식 × 모델별 지연·오차·메모리·전력 표, 결론

### 생각해 볼 점
- CPU로도 1ms면 충분히 빠른데, 왜 굳이 변환하나? (힌트: 동시에 올라갈 다른 모델들, 전력, 공간 수 확장)
- 순환 신경망(GRU/LSTM)과 합성곱 모델(TCN) 중 무엇이 변환 후 더 빨라지나? 이유는?
- 평균 지연보다 '느린 쪽 5%'가 상시 서비스에서 더 중요한 이유는?

### 심화(B)
- INT8 변환을 시도하고, 정확도 손실과 속도 이득을 비교한다.
- 모델 4개를 동시에 올렸을 때의 총 메모리를 재고, 로컬 LLM과 함께 올릴 수 있는 조합을 제안한다.

## 과제 8. 상시 추론 서비스

### 상황
지금까지의 결과는 '실험'이다. 운영진에게는 **매분 최신 판단을 내놓는 서비스**가 필요하다. 다른 팀의 대시보드, 다음 주 만들 로컬 LLM 에이전트, 냉난방 제어 시스템이 이 서비스를 가져다 쓴다.

### 해결할 것
1. **매분 자동으로** 공간마다 아래 세 가지를 계산한다.
   - 60분 예측(CO₂·온도), 그리고 "몇 분 뒤 1,000ppm 초과" 같은 **바로 쓸 수 있는 경보**
   - 이상 여부, 이상 점수, 원인 센서, 규칙 경보(데이터 끊김·값 고정·범위 밖)
   - 사용 여부와 환기 선제 경보
2. **두 가지 방식으로 제공한다.**
   - MQTT 발행: 새로 접속한 구독자도 최신값을 바로 받을 수 있어야 한다
   - 조회 API: "회의실 30분 뒤 CO₂는?"처럼 필요할 때 물어볼 수 있어야 한다
3. **학습 때와 똑같은 전처리**를 거친다. 서비스와 학습의 전처리가 다르면 어떤 일이 생기는지 설명한다.
4. **장애에 버틴다.**
   - 데이터가 일부 끊겨도 서비스는 계속 돌고, 끊긴 사실을 알린다
   - 한 번 계산이 실패해도 다음 주기에는 정상으로 돌아온다
   - 보드를 재부팅하면 자동으로 시작된다
5. **결과 형식을 문서로 남긴다.** 다른 팀이 이 문서만 보고 쓸 수 있어야 한다.

### 확인 기준
- **12시간 무중단** 가동 기록
- 가동 중 수집기를 10분 멈췄을 때 '데이터 끊김' 경보가 나고, 다시 켜면 정상으로 돌아온다
- 조회 API로 공간별 예측·이상·상태를 받을 수 있다
- 결과 형식 문서(토픽·필드·단위·예시)

### 산출물
- **예측 서비스 v1**(상시 운영 상태)
- 12시간 가동 로그 요약(주기별 처리 시간, 경보 발생 내역, 장애 시험 결과)
- 결과 형식 문서

### 생각해 볼 점
- 5분 단위로 모으는데, 막 시작된 5분 칸(아직 1~2분치만 있음)을 써도 될까?
- 같은 고장에 대해 매분 경보를 보내면 어떻게 되나? 경보를 언제 다시 보내야 하나?
- 다음 주 로컬 LLM이 이 서비스를 '도구'로 쓰려면 결과에 무엇이 더 있어야 할까?

### 심화(B)
- 예측 결과로 환기·냉난방 제어 규칙을 설계하고, 지난 1주 데이터에 적용했을 때 1,000ppm 초과 시간이 얼마나 줄었을지 추정한다.
- 서비스가 스스로 성능을 감시하게 한다. 예측이 맞았는지 60분 뒤에 채점하고, 오차가 커지면 알린다.
